# tandem — агент тарифных кампаний

Beeline Tariff Marketing Campaigns Case.

Агент исследует аудиторию пилотами и выбирает до 10 маркетинговых
кампаний, максимизируя ожидаемый прирост ARPU за вычетом стоимости контактов.
Все предоставленные данные синтетические: результаты не описывают реальный
бизнес Beeline.

## Текущее состояние

Реализован `agent.py` с интерфейсом `Agent().act(env)`. Агент обновляет оценки
эффектов после пилотов и подбирает непересекающиеся аудитории, каналы и охват
с учётом оставшихся денег и контактов. `submission.csv` сформирован официальным
`build_submission` с seed 42. Журнал решений — `reports/decision_trace.json`.

Локальный benchmark `Agent` на seed 0–9 дал положительный чистый результат
во всех 10 прогонах; медиана 1 434 332 у.е. Подробные результаты для
коммита `409d9c0` и текущей версии — в
[`reports/benchmark-agent.md`](reports/benchmark-agent.md). Это результаты
синтетической мок-среды, а не прогноз оценки жюри. Числа в журнале решений —
наблюдения пилотов и оценки алгоритма, а не измеренная итоговая прибыль.
Отчёт `reports/baseline.json` относится только к исходному `agent_template`:
у него 0 положительных результатов на seed=0..9.

## Разбор плана для аналитика

Скачайте и откройте [`reports/decision_report.html`](reports/decision_report.html)
в браузере: три кампании, расход ресурсов, связанные пилоты и происхождение
каждой оценки. Можно фильтровать журнал и скачать исходные CSV/JSON.
Все данные встроены в HTML; сервер, сеть и API-ключи для просмотра не нужны.
GitHub показывает исходник HTML, поэтому файл нужно открыть локально.

Обновить отчёт из сохранённого CSV и журнала:
`.venv\Scripts\python.exe tools/render_decision_report.py` (Windows) или
`.venv/bin/python tools/render_decision_report.py` (Linux/macOS).
Генератор проверяет хеши и согласованность входов, не запускает агента заново.
[Устройство отчёта и сценарий просмотра](docs/decision_report.md).

### Новый расчёт одной командой

После установки зависимостей можно заново выполнить весь сценарий:

```powershell
.venv\Scripts\python.exe tools/run_demo.py
```

Linux/macOS: `.venv/bin/python tools/run_demo.py`.

Команда дважды запускает агента на официальном mock с seed 42, требует
одинаковый CSV, сверяет целостность результата и создаёт интерактивный HTML.
В конце печатается путь к отчёту. Откройте его в браузере.

Каждый запуск получает отдельную папку `reports/demo_runs/run_.../` с CSV,
JSON, HTML, логами и `run_status.json`. Старые результаты не используются.
Корневой `submission.csv` и сохранённые артефакты сдачи не заменяются.
Демо-запуски исключены из Git. При ошибке команда возвращает ненулевой код,
а папка сохраняется с диагностикой; `complete` появляется только после
успешного экспорта и генерации отчёта.

Полный сценарий выполнен из архива `7d585c4`, в который намеренно не включены
корневой CSV и вся папка `reports/`: результат создан заново за 2,875 секунды
на локальной машине. [Журнал запуска](reports/fresh_demo_check.json).
Время зависит от компьютера; это воспроизведение mock, не оценка скрытых эффектов.

## Установка и запуск

Требуется Python 3.12. Проверено на CPython 3.12.13, pandas 3.0.6, numpy 2.5.3.
Команды выполняются из корня репозитория. GPU, API-ключи и платные аккаунты
для работы агента не нужны.

```bash
python -m venv .venv
# Windows PowerShell:
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe tools/verify_submission.py
```

Linux/macOS после создания окружения:

```bash
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python tools/verify_submission.py
```

Ожидаемый результат проверки: строки `OK`, итоговое `"passed": true` и код
выхода 0. Проверяется уже сохранённый CSV: исходники и данные сверяются с
контрольными суммами, затем отдельный процесс дважды генерирует результат
временной папки. Исходный `submission.csv` и журнал не перезаписываются.
`FAIL` и ненулевой код выхода означают, что причину нужно устранить.

Чистый архив коммита `4887534` проверен в новом виртуальном окружении
Windows / Python 3.12.13 с установкой зависимостей по инструкции выше:
32 проверки пройдены, CSV воспроизведён полностью. Результат и версии —
[`reports/release_check.json`](reports/release_check.json).
Первоначальная проверка выявила различие контрольных сумм из-за CRLF/LF;
её результат сохранён в
[`reports/release_check_initial.json`](reports/release_check_initial.json),
исправление — нормализация текстовых файлов при расчёте сумм.

После изменения алгоритма обновите артефакты командой
`.venv\Scripts\python.exe tools/export_strategy.py` (Windows) или
`.venv/bin/python tools/export_strategy.py` (Linux/macOS), затем повторите проверку.
Результат экспорта: `submission.csv` и `reports/decision_trace.json`. Скрипт экспорта
вызывает официальный `build_submission`; журнал дополнительно содержит
пилоты, оценки, расходы и SHA-256 исходников, входных данных и итогового CSV.
Перед записью экспорт дважды формирует CSV с seed 42 и требует полного совпадения.
Агент проверяет допустимость и отсутствие пересечений финального плана перед
возвратом результата; отчёт сохраняет `preflight` и полный расход вместе с пилотами.
При ошибке генерации существующие артефакты не заменяются. Стандартная команда
`.venv\Scripts\python.exe make_submission.py` (Windows) формирует тот же формат
CSV без журнала; Linux/macOS используют `.venv/bin/python`.

Запускайте проект целиком из репозитория. Одних `agent.py` и `submission.csv`
недостаточно: агент импортирует `strategy/` и `validation/`, использует историю
`data/change_tariff.csv`; локальной среде также нужны `customer_profile.csv` и
`data/dict_tariff.csv`. Организаторские файлы включены в репозиторий.

В среде организатора достаточно `from agent import Agent; Agent().act(env)`.
Состояние создаётся заново на каждый вызов; собственной случайности и внешних
API нет. Для исторических данных используется путь относительно `agent.py`.

Пути экспорта внутри проекта ограничены корневым `submission.csv` и
директорией `reports/`. Это защищает исходные данные и код от случайной
перезаписи параметрами `--out` / `--trace`. Контрольные суммы текстовых файлов
рассчитываются после приведения CRLF к LF (`sha256-text-lf-v1`), чтобы они
не менялись из-за платформы или нормализации при Git checkout.

## Архитектура

```text
customer_profile.csv + data/ + справочники
                 ↓
Agent.act(env): выбор пилотов → обновление оценок → план кампаний
                 ↓
публичный scoring_core.py → чистый прирост, расходы, охват
                 ↓
make_submission.py → воспроизводимая таблица финальных кампаний
```

`tools/run_baseline.py` импортирует неизменённый `agent_template.Agent` и
использует официальные `evaluate_agent` и `build_submission`.
Собственная реализация:

| Файл | Назначение |
|---|---|
| `agent.py` | Выбор следующего пилота, обновление знаний, финальное решение |
| `strategy/beliefs.py` | Робастная история и обновление оценок по наблюдениям |
| `strategy/portfolio.py` | Аудитории, выбор каналов, бюджет и отсутствие пересечений |
| `tools/export_strategy.py` | Воспроизводимый экспорт и объяснение решений |
| `tools/verify_submission.py` | Проверка сохранённого CSV, контрольных сумм и запуска из отдельного процесса |
| `tools/run_demo.py` | Новый полный запуск: агент → проверка → интерактивный отчёт |

## Как принимаются решения

1. Исторические изменения ARPU ограничиваются диапазоном от −1 до 2,
   знаменатель защищён от почти нулевой выручки. Малые группы сглаживаются
   преимущественно по тому же ARPU-сегменту. Историческая частота переходов
   не принимается за вероятность конверсии.
2. Начальные пилоты охватывают разные ARPU-сегменты и текущие тарифы.
   Затем следующий пилот выбирается по ожидаемой ценности информации,
   выручке аудитории, уже найденным альтернативам и стоимости контактов.
   Размер выбирается между 100 и 200, с уменьшением по фактическим лимитам.
3. Наблюдения обновляют среднее и неопределённость с учётом фактического
   размера выборки и публичного шума 0,804 / sqrt(n). История остаётся слабым
   предположением: большой пилот имеет существенно больший вес.
4. Последние доступные пилоты могут повторно исследовать перспективные
   предложения. Для планирования из среднего вычитаются 1,65 стандартного
   отклонения. Это поправка на риск, не гарантия доходности или одновременная
   доверительная граница для всех выбранных гипотез.
5. Для каждой исследованной ячейки рассматриваются целая аудитория и
   срезы по потреблению интернета/звонков. Подбор перебирает цены ограниченных
   ресурсов и улучшает комбинацию заменой кампаний. Выбранные финальные
   аудитории не пересекаются и целиком помещаются в лимиты.
6. Все каналы сравниваются после стоимости контакта. Для канала с множителем
   выше единицы положительный эффект оценивается консервативно из-за возможного
   насыщения конверсии. Неизвестные ID участников пилотов не читаются;
   ожидаемое пересечение с пилотами учитывается вероятностно.

На разведку резервируется до 18% начального денежного бюджета; при его
исчерпании доступен бесплатный канал. Часть охвата сохраняется для финала.
Если прибыльных по оценке вариантов нет, обязательная единственная кампания
выбирается по минимальному ожидаемому совокупному ущербу среди допустимых
исследованных вариантов. Это не обещание положительного результата.

## Ограничения модели

- Отбор портфеля эвристический: глобальный математический оптимум не заявляется.
- История содержит отобранных клиентов, уже сменивших тариф, и может отличаться
  от текущей аудитории. Априорные предположения не заменяют пилоты.
- Из-за ограниченного числа пилотов часть прибыльных предложений может остаться
  неизученной; шум способен повлиять на выбор и знак фактической прибыли.
- Профили с пропущенным тарифом/ARPU-сегментом не включаются в исследуемые ячейки.
  Некорректные значения baseline имеют нулевую ценность при планировании,
  но соответствующие строки продолжают учитываться в стоимости и охвате.
- Оценка пересечения с пилотами приближённая; точные ID публичный интерфейс
  не раскрывает. Финальная таблица содержит только финальные кампании.

[Эксперимент точного выбора каналов](docs/channel_allocation.md) сохранён
отдельно и не используется основным агентом: дополнительные запуски выявили
ухудшение фактического результата при улучшении расчётной оценки.

[Исследование размеров пилотов и ранней остановки](docs/pilot_research.md)
также завершилось отказом от переноса вариантов в основной агент.
Малые первые пилоты снизили медиану mock примерно на 24%. Ранняя остановка
уменьшила потери в отрицательных сценариях, но на отдельных seed 30–49
обнаружение редкого выгодного предложения упало с 12/20 до 1/20.
Исходники экспериментов и полные результаты сохранены для воспроизведения.

[Сравнение адаптивной разведки с заранее составленным расписанием](docs/adaptivity_ablation.md)
использует одинаковый финальный планировщик: 140 попыток, 70 пар, семь
синтетических моделей, seed 50–59. Результаты смешанные: адаптивный агент
выигрывает все десять пар в `mixed_2`, фиксированный — все десять в `rare_1`.
В обеих `rare`-моделях ни одна политика не обнаружила выгодное сочетание.
Общее превосходство не доказано; рабочий алгоритм сохранён, полные ухудшения
и ограничения приведены в отчёте.

## Данные и ограничения

- 23 441 уникальный абонент, 21 тариф, 14 823 строки истории переходов.
- Бюджет 100 000 у.е.; до 15 000 контактов вместе с пилотами.
- До 20 пилотов по 10–200 абонентов; 1–10 финальных кампаний;
  до 5 000 контактов на кампанию.
- Повторные контакты расходуют ресурсы; эффект человека учитывается один раз.
- Пилоты шумные, эффекты на судействе отличаются от локальной модели.
- В профиле есть пропуски, включая 95 отсутствующих текущих тарифов.
- `PASS` локального оценщика означает положительный net, но не заменяет
  проверку всех must-have.

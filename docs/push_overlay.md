# Бесплатные Push по доказанно охваченным аудиториям

## Что изменено

После неизменённой разведки и базового финального плана агент добавляет
бесплатные Push только там, где предшествующий охват доказан публичными данными.
Основание — точная аудитория базовой кампании либо целая ячейка тарифа/ARPU,
которую полностью покрыл **один** пилот. Целевой тариф добавления уже должен
быть исследован в той же ячейке. Новых пилотов этот этап не запускает.

В текущей реализации `agent:BaselineAgent` сохраняет исходную политику,
`agent:Agent` добавляет этот этап. Реализация:
[strategy/full_coverage_push.py](../strategy/full_coverage_push.py), независимая
проверка: [validation/overlay.py](../validation/overlay.py). Числовые оценки
базы и фактические дополнительные контакты разделены в
[интерактивном отчёте](decision_report.md#бесплатные-добавления-и-два-уровня-плана).

## Условное доказательство механизма

[Опубликованный scorer](../scoring_core.py) учитывает клиента один раз,
по максимальному эффекту всех его кампаний, затем вычитает стоимость контактов.
Если прежний лучший эффект клиента равен `g`, а эффект добавленного Push — `h`,
новый результат клиента равен `max(g, h) >= g`.

Из этого следует неубывание net **при одновременном выполнении условий**:

- неизменны пилоты, их результаты и весь исходный финальный префикс;
- новые кампании добавлены после базы и стоят ровно ноль;
- каждый их клиент уже контактирован пилотом или базовой кампанией;
- все эффекты конечны, а исходные и новые кампании не отбрасываются и не
  обрезаются: соблюдены бюджет, 15 000 контактов вместе с пилотами, 10 финальных
  кампаний и 5 000 клиентов на кампанию.

Предыдущий охват пилотом доказывается равенством **фактического** `n_customers`
одного пилота размеру его точной публичной ячейки. Среда выбирает без возвращения,
а базовый агент проводит пилоты по целой ячейке тарифа/ARPU. Сумма частичных
пилотов, положительный ответ и ожидаемый процент покрытия доказательством
не являются. Агент не читает приватные ID выбранных участников.

Повторные контакты расходуют лимит. Уникальная аудитория финальных кампаний
может увеличиться за счёт уже покрытой пилотом ячейки; уникальная аудитория
**всего запуска с пилотами** не увеличивается. Неубывание не означает строгое
улучшение или положительный итог. В реальной рассылке возможны усталость
аудитории и взаимодействие предложений — опубликованный scorer этого не моделирует.

## Как выбираются добавления

Кандидаты копируют фильтры разрешённой аудитории. Приоритет — её сумма baseline,
умноженная на ожидаемую положительную часть разности двух нормальных оценок,
ограниченную диапазоном [0, 2]. Для того же target используется общее случайное
значение; для разных targets — приближение независимости. Насыщение каналов
и покрытие пилотами в этом **ранжирующем proxy** не моделируются.

Кандидаты сортируются один раз; добавляются только допустимые, без одинаковых
комбинаций Push/target/фильтры. Proxy не является измеренной прибылью и не
суммируется по пересекающимся кампаниям. Точность ранжирования влияет на размер
возможной прибавки, но не доказывает и не заменяет перечисленные условия.

## Версии и план измерений

Первый кандидат повторял только базовые финальные аудитории: на development
получены 3 улучшения и 45 равенств из 48 пар. После просмотра этой серии
сформулирован **второй** кандидат с полностью покрытыми пилотами ячейками.
Его нельзя описывать как выбранного до всех development-результатов.

Второй кандидат и протокол зафиксированы в
`fbcd614bea7d9c4a5d63f3ef0f3b199aa7ab5af0` до открытия holdout.
Development: 12 прежних моделей и четыре новые конфигурации, seed 60–62,
48 пар. Holdout: те же 12 прежних моделей и четыре другие заранее заданные
конфигурации, seed 70–79, 160 пар. Исходники holdout:
`ce20a91ddb04b0e89a44f5b59ed2471f7056d07e`; хеши до/после совпали.
Окружение обеих серий: CPython 3.12.13, NumPy 2.5.3, pandas 3.0.6.

Новые development-конфигурации: 2 160 клиентов, пять тарифов, 60 переходов;
holdout: 2 700 клиентов, шесть других тарифов, 90 переходов. Семейства — mixed,
negative, rare и high_conversion. Размещение положительных переходов случайно
и независимо от размеров ячеек, истории и действий агента. В новом holdout
количества положительных переходов — соответственно 36, 0, 1 и 36.
Раздельные генераторы задают профиль, эффекты и размещение положительных
переходов. [Точные конфигурации и хеши](../reports/push_overlay/scenario_designs.json),
[код конфигураций](../experiments/push_overlay/scenarios.py),
[зафиксированный протокол](../experiments/push_overlay/full_coverage_protocol.md).

Измеритель использует неизменённый официальный scorer. В каждой паре проверяет
совпадение модели, профиля, реальных pilot IDs и наблюдений, неизменность
финального префикса, включение добавлений в ранее контактированную аудиторию,
одинаковые расходы и уникальную аудиторию всего запуска, допустимость и caps.
Приватные ID доступны только измерителю, не политике.

## Измеренные результаты

Development v2: **40 улучшений, 8 равенств, 0 ухудшений**, 48 допустимых пар.

0 ошибок. Улучшение означает попарную разницу net больше `1e-6`, а не победу
над другими командами. Все проверки механизма прошли. Денежные значения —

это не доказательство устранения прежней проблемы обнаружения редких предложений.

Перенос в продукт дополнительно требует согласованности trace, полного CSV,
независимой валидации, отчёта и воспроизводимости.

## Воспроизведение

Исторический harness импортирует `agent:Agent` как старую базу. Поэтому для
повторения **именно этой пары политик** нужен отдельный checkout `bcdea1d`,
где production ещё не включал добавления. Из корня Git-репозитория:

```powershell
git worktree add --detach ../tandem-push-reproduction bcdea1d
cd ../tandem-push-reproduction
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe experiments/push_overlay/measure.py --phase development --candidate experiments.push_overlay.full_coverage_agent:FullCoveragePushAgent --seeds 60:63 --out reports/push_overlay/rerun_full_development.json
.venv\Scripts\python.exe experiments/push_overlay/measure.py --phase holdout --candidate experiments.push_overlay.full_coverage_agent:FullCoveragePushAgent --seeds 70:80 --out reports/push_overlay/rerun_full_holdout.json
```

Нужен Python 3.12; на Linux/macOS используйте `python3.12` и `.venv/bin/python`.
Имя worktree и выходных файлов должно быть новым. Повторные результаты относятся
к SHA повторения; оригинальные JSON не перезаписываются.

В **текущем продукте** исходная политика называется `agent:BaselineAgent`,
а дополненная — `agent:Agent`. Экспериментальные классы и runner также
переключены на явный `BaselineAgent`, чтобы избежать двойного дополнения.
AST алгоритма сохранён; [проверки переноса](../tests/test_push_port.py)
сопоставляют его с замороженной версией и проверяют действия на пяти сценариях.
Их можно независимо измерить штатным benchmark:

```powershell
.venv\Scripts\python.exe tools/benchmark.py --agent agent:BaselineAgent --seeds 70:80 --out reports/rerun_push_base.json
.venv\Scripts\python.exe tools/benchmark.py --agent agent:Agent --seeds 70:80 --out reports/rerun_push_product.json
```

Эти две команды проверяют публичный mock, не воспроизводят все 16 моделей
исторического harness и не заменяют его проверки парности. Новые seed известных
моделей изменяют шум, а не создают независимую скрытую среду.

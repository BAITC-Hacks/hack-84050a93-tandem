## 3. Суть технической задачи

Маркетинговый агент исследует синтетическую аудиторию пилотами и выбирает
маркетинговые кампании. Кампания задаёт текущую аудиторию, целевой тариф
и канал. Оптимизируем net = суммарный эффект по уникальным абонентам минус
стоимость всех контактов. Baseline ARPU уже дан в predicted_arpu.

Публичный интерфейс:

```python
class Agent:
    def act(self, env) -> list[dict]:
        # env.customer_profile, env.tariffs, env.channels
        # env.remaining_budget, env.remaining_contacts, env.pilots_left
        # env.run_pilot(...), env.pilot_history
        ...
```

run_pilot принимает target_tariff, channel, n_customers и фильтры
filter_arpu_segment / filter_data_segment / filter_call_segment /
filter_current_tariff. Ответ содержит observed_lift_ratio,
observed_lift_total, n_customers, cost, remaining_budget, remaining_contacts.
Использовать фактическое n_customers, а не запрошенное.

Финальные кампании:

```python
{
    'campaign_name': 'stable_name',
    'filter_arpu_segment': 'HIGH',
    'filter_data_segment': 'HEAVY',
    'filter_call_segment': None,
    'filter_current_tariff': 'tariff_4;tariff_8',
    'target_tariff': 'tariff_10',
    'channel': 'sms',
}
```

Фильтры необязательны, но значения должны быть корректными. ARPU:
LOW/MID/HIGH; data: NON_USER/LITE/HEAVY; calls: LOW/MEDIUM/HIGH.
Несколько текущих тарифов разделяются `;`. Произвольные explicit_ids не
входят в официальный формат финального CSV.

Одновременно действуют лимиты:
- 1–10 финальных кампаний;
- до 5 000 абонентов на кампанию;
- до 15 000 контактов вместе с пилотами;
- до 100 000 у.е. вместе с пилотами;
- до 20 пилотов по 10–200 абонентов.

Каналы: push — цена 0, множитель 0.50; sms — 4 и 0.65;
digital_ads — 22 и 0.85; call — 160 и 1.20.
Бесплатный push всё равно расходует контакты и может иметь отрицательный эффект.

Must-have: agent.py / Agent.act; корректные 1–10 кампаний; пилоты и использование
их результатов; соблюдение ограничений; воспроизводимый submission.csv.
README и requirements обязательны для нашей команды. В Google ТЗ rubric:
работоспособность 25, реализация 25, README/воспроизводимость 25,
ценность 15, потенциал/оригинальность 10.

## 4. Уже установленные факты и ловушки

- customer_profile.csv: 23 441 строка и уникальный ID_NUMBER;
  change_tariff.csv: 14 823 перехода; dict_tariff.csv: 21 тариф;
  traffic.csv: 75 736 строк; arpu_monthly.csv: 78 798 строк.
- Пропуски есть: current_tariff у 95 клиентов, arpu_segment у 5,
  data_segment у 110. Не заменять отсутствующие значения произвольной категорией.
- История — другая выборка, это prior, а не истинная модель аудитории судейства.
- Факты о реальном бизнесе Beeline из этих данных выводить нельзя.
- Шум пилота в публичной среде ~0.804/sqrt(n). Один положительный пилот
  не доказывает прибыльность. Агент должен оценивать неопределённость.
- Канал умножает конверсию, ограниченную сверху 1; учитывай насыщение,
  не предполагай безусловную линейность дорогих каналов.
- Порядок кампаний влияет на обрезание по деньгам/контактам.
- Повторные контакты стоят денег, но эффект человека учитывается по лучшей
  кампании один раз. Пилоты тоже участвуют в общем эффекте и расходах.
- env.remaining_* показывает остатки после пилотов, не после финального списка.
- local_eval PASS означает net>0, а не прохождение всех требований сдачи.
- make_submission.py использует seed 42; сравнивается повторное получение
  тех же финальных кампаний. Собственная случайность и LLM могут нарушить это.
- Исходный шаблон: 0 положительных результатов на seed=0..9;
  seed42 net около −1 035 279; seed3 возвращает 0 финальных кампаний.
  Это baseline, не результат нашей стратегии и не прогноз итогового места.
- Есть расхождение: ТЗ допускает 10 минут и LLM API, комментарий шаблона —
  5 минут и offline. Наше ядро должно работать локально, желательно заметно быстрее
  5 минут. Не делать внешнюю модель обязательной зависимостью проверок.
- Соотношение рейтинга по net и общей рубрики уточняет капитан; не обещать победу
  на основании одного хорошего числа в mock.

Запрещено добывать скрытую impact-модель через __closure__, gc,
introspection, файлы организатора или другие обходы. Не менять официальный
скорер или mock ради улучшения отчётов. Не импортировать _mock_impact_model
в продакшен-агент как источник истинных ответов. Публичный evaluator можно
использовать в тестовом harness по назначению.

разброс, размер текущей аудитории и её суммарный predicted_arpu.

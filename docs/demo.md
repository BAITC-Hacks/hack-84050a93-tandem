# Сценарий демонстрации tandem

## 1. Задача

Агент получает синтетический профиль абонентов, справочник тарифов и четыре канала. Он может провести до 20 шумных пилотов, а затем должен вернуть 1–10 кампаний. Цель — максимизировать прирост `predicted_arpu` по уникальным клиентам за вычетом стоимости всех контактов при общем бюджете 100 000 и лимите 15 000 контактов.

Важно: история переходов и локальная mock-модель не описывают реальный Beeline и не совпадают со скрытой моделью судейства. Поэтому решение не заучивает «лучший тариф», а использует историю как слабый prior и обновляет решение по пилотам.

## 2. Что показал аудит

```bash
python tools/analyze_data.py
```

- В профиле 23 441 уникальный клиент; 95 строк без текущего тарифа, 5 без ARPU-сегмента и 110 без data-сегмента. Пропуски не заменяются вымышленной категорией.
- ID текущего профиля не пересекаются с ID исторических таблиц: персональное присоединение истории невозможно, допустимы только агрегированные гипотезы.
- История смещена: HIGH составляет 59.4% текущего профиля, но 34.8% пригодной части истории. В 2 118 из 14 823 переходов baseline ARPU ниже 100, поэтому raw относительные изменения нестабильны.
- `reports/candidate_priors.csv` хранит медиану, обрезанное среднее, разброс, размер истории и текущей аудитории. Только 104 из 451 комбинации имеют хотя бы 30 исторических наблюдений; все кандидаты всё равно требуют пилота.

## 3. Стратегия пилотов и кампаний

1. Сформировать ячейки `current_tariff × arpu_segment` с достаточной аудиторией и положительным baseline.
2. Построить слабые частично сглаженные priors по истории и характеристикам тарифов.
3. Распределять пилоты между ARPU-стратами, оценивая ценность дополнительной информации; поздние пилоты подтверждают вероятных победителей и уменьшают selection bias.
4. Обновить оценки эффекта и неопределённости по фактическому `n_customers` каждого пилота.
5. Создать варианты непересекающихся аудиторий и каналов; отбирать только пилотированные target, штрафовать риск и учитывать остатки бюджета/контактов.
6. Перед сдачей прогнать независимый `validate_plan`, который проверяет фильтры, размер каждой аудитории, общий расход и пересечения.

## 4. Измеренный результат против шаблона

Оба варианта запущены на одинаковых seed 0–9 официальным публичным evaluator. Это проверка механики на mock, а не прогноз судейства.

| Вариант | Положительных | Медиана net | Минимум | Максимум | seed42 воспроизводим |
|---|---:|---:|---:|---:|---:|
| Исходный `agent_template:Agent` | 0/10 | −357 947.80 | −1 019 431.06 | −76 493.45 | да |
| Текущий `agent:Agent` | 10/10 | 1 434 332.15 | 1 058 935.01 | 1 609 503.85 | да |

Все 10 запусков каждого агента завершились без исключений и timeout. Полные попытки, включая расходы, контакты, число пилотов и кампаний, находятся в `reports/benchmark_template.*` и `reports/benchmark_agent.*`.

## 5. Ограничения и честная интерпретация

- Хороший результат на mock не гарантирует положительного результата на скрытой модели.
- Синтетический stress-test сохранил слабые результаты: агент отрицателен 5/5 при всех отрицательных эффектах и 5/5 в сценарии с редким хорошим сегментом из 12 клиентов. Отрицательный итог сам по себе не доказывает, что сегмент не найден: для этого нужен журнал действий. Это искусственные сценарии, не скрытые тесты организатора.
- При слабом сигнале и шумных пилотах результат меняется: в пяти искусственных запусках минимум net 46 814.80 против максимума 94 244.52, хотя все остались положительными.
- Финальный preflight seed42 после 20 пилотов валиден: 3 кампании, 2 476 финальных контактов, 16 632 стоимости и без пересечений. Пилоты уже потратили 3 500 контактов и 14 000 бюджета.
- Эффекты реального бизнеса, проценты экономии и место в рейтинге из этих экспериментов не выводятся.

## 6. Воспроизводимый запуск

```bash
python -m pip install -r requirements-dev.txt
python tools/analyze_data.py
python -m pytest -q
python tools/benchmark.py --agent agent_template:Agent --seeds 0:10 --out reports/reproduced_template.json
python tools/benchmark.py --agent agent:Agent --seeds 0:10 --out reports/reproduced_agent.json
python tools/stress_benchmark.py --agent agent:Agent --seeds 0:5 --out reports/reproduced_stress.json
python local_eval.py --runs 10
python make_submission.py
```

Для сдачи капитан проверяет, что повторный `make_submission.py` даёт тот же seed42 CSV, затем отправляет оцениваемую версию до дедлайна. Git push сам по себе не заменяет отправку формы на платформе.
